# 종가 관심종목 알림 구현 검토 결과

검토일: 2026년 10월 23일. [최초 설계](../plans/2026-10-23-stock-alerts.md), [운영 절차](../stock-alerts-operations.md).

실제 Orca 작업자 네 명이 비판·가능성·외부인·확장성 관점으로 독립 정적 검토했다. 모두 기본 Codex 설정을 사용했고 누락이나 공급자 대체는 없다. 네 명 모두 완료 보고를 확인한 뒤 해제했다. 구현과 실행 검증은 주 세션이 담당했다.

## 구현 범위

- 10종 종가 조건 평가, 계정별 관심종목·일괄 규칙·수신 동의 API, PostgreSQL 마이그레이션과 동시 실행 제어.
- 한국·미국 거래일 달력, 90분 마감 여유, 동일 스냅샷 5분 간격 확인, 분할 가격·거래량 보정, 과거 정정 표시.
- 일일 run 재개와 5세션 소급, 이벤트·발송 원장, 동일 본문·멱등 키 재시도, 해지와 서명 웹훅, legacy 리밸런싱 통합 전환.
- `/alerts`의 검색·템플릿·여러 종목 등록·수정·정지·재개·보관·이력·로딩·입력 보존·모바일 화면.

## 검토 지적과 조치

| 지적 | 반영한 조치 |
| --- | --- |
| 삭제한 규칙이 숨겨진 UNIQUE 제약 때문에 영구 재등록 불가 | 동일 규칙을 보관 상태로 유지하고 사용자 명시적 재사용 선택 시 의미 버전·활성 시각을 새로 부여. 자동 복원하지 않음 |
| 조회 실패를 정상 무신호처럼 표시 | 규칙에 최신 보류 결과를 기록하고 일별 결과를 deferred로 구분. 비밀 본문을 노출하지 않고 보류 수만 API에 제공 |
| 편집 revision 충돌 후 초안 복구 불가 | 초안을 유지한 채 최신 조건을 확인하고 적용 여부를 선택하는 별도 동작 제공 |
| 발송 접수 결과와 웹훅 동시 커밋 시 반송 누락 | 공급자 메일 ID별 transaction advisory lock으로 두 경로 직렬화. 중복 receipt도 재적용 |
| 만료 해지 토큰이 동시 재동의를 취소 | 토큰 버전 조건과 해지 UPDATE를 한 SQL 문장으로 처리 |
| 삭제·발송·웹훅 잠금 순서 역전 | 사용자 행을 먼저 잠그고 digest를 재조회하는 공통 순서로 정리 |
| 사후 종가·분할 정정이 이력에 남지 않음 | 이전 자료와 겹치는 구간 변경 시 기존 이벤트를 재평가하고 전후 해시·정정 이유 기록. 자동 정정 메일은 보내지 않음 |
| 거래정지와 미확인 누락을 구분 못함 | 근거 URL이 있는 운영자 확인 거래정지 목록을 지원. 미확인 누락은 계속 보류하며 가짜 봉을 만들지 않음 |
| 운영자 Blob 장애가 전체 사용자 발송을 중단 | 리밸런싱 섹션의 오류를 별도 보류 안내로 처리해 다른 종목 신호와 사용자 발송은 계속 진행 |
| 마지막 호출의 429 미접수 신호가 다음 날 소급에서 영구 제외 | 명백한 미접수와 결과불명을 구분. 다음 날 missed_window 확정 후 전자만 소급 가능, unknown은 새 키로 재전송 금지 |
| 본문 재생성 반복으로 발송이 시간 예산에 밀림 | 준비된 원장은 재사용하고 사용자별 준비 예산을 적용. 이벤트별 종목 메타데이터 추가 조회를 JOIN으로 제거 |
| 알림 데이터 삭제 후 legacy 메일 부활 가능 | 주소를 지워도 영구 전환 표식으로 기존 Cron을 억제 |

## 실행 검증

최종 Python 전체 회귀는 260개 통과이며, opt-in 부하 1개는 기본 실행에서 제외하고 별도 실행으로 통과했다. 기존 Node 회귀 25개와 신규 Chrome 검사도 통과했다. 운영 자격증명은 테스트 초기화에서 제거하고 DB 통합 테스트는 명시한 전용 시험 URL만 사용한다.

실제 PostgreSQL 17의 격리된 `alerts_test` DB에서 계정 격리, 일괄 등록 원자성, UNIQUE 경합, revision, lease fencing, 응답 유실, 해지, 조기·동시 웹훅, 정정, 자료 실패를 검사했다. 메모리 저장소나 SQLite로 동시성 검사를 대체하지 않았다.

Chrome에서 10종 선택, 관심종목·규칙 등록, 정지, 악성 이름의 텍스트 표시, 로딩, 오류 입력 보존, 편집 충돌 해소와 모바일 가로 넘침을 검사했다. 화면 네트워크는 고정 API 응답이며, DB API는 별도 PostgreSQL 통합 테스트로 검증했다.

첫 50계정·100종목·5,000규칙 부하 검사는 신호 5,000개와 메일 50통을 중복 없이 처리했으나 첫 호출 약 216초로 210초 기준을 넘겼다. 평가 중단 시점을 150초로 앞당기고 준비·발송에 시간 여유를 남긴 뒤 재검사했다.

재검사에서는 호출 약 156.9초·81.6초의 두 번으로 완료했다. 고유 종목 조회 100회, 신호 5,000개, 접수 50통이며 중복 조회·발송은 없었다. 시세와 메일은 고정 가짜 응답이고 DB는 실제 PostgreSQL이다. 이 수치는 로컬 실행 결과이며 Vercel·Neon·실공급자 지연과 quota에서의 성능을 보장하지 않는다.

## 남은 운영 검증과 차이

- 실제 PostgreSQL 운영 배포, 시세 계약·한국 ETF 커버리지·기업행동 응답 대조, Resend 도메인과 실제 메일·웹훅 검증은 미실시다.
- 분 Cron은 플랜 미확인으로 기본 배포에 자동 추가하지 않았다. Pro 확인 후 `vercel.stock-alerts.json`을 적용한다. 기존 일일 Cron은 유지한다.
- 운영자 전용 통합 상태 화면은 별도로 만들지 않았다. 사용자는 본인 화면에서 결과를 보고 운영자는 run/task/digest DB와 Cron 집계로 확인한다.
- 거래정지 확인 자료는 자동 수집하지 않는다. 근거 있는 운영 목록을 사용하며 근거가 없으면 보류한다.
- 기존 데이터 정정 비교는 저장된 180일 내 이벤트를 대상으로 하며, 정정 때문에 이전에 없던 과거 신호를 새로 발송하지 않는다.
- 실제 발송은 기본 OFF다. DB·발신·시세 설정과 운영 검증을 마친 후 활성화한다. 신규 로그인 자체는 수신 동의가 아니다.
