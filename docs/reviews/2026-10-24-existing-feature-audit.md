# 기존 기능과 테스트 점검

이 문서는 수정 전 감사 기록이다. 후속 수정과 검증 결과는 [저장 복구 수정 기록](2026-10-24-save-recovery-fixes.md)을 참고한다.

점검일: 2026년 10월 24일 한국시간. 기준 커밋은 `720e185`이며, 이전 작업의 포트폴리오 ETag 수정과 회귀 테스트가 있는 작업 폴더를 검사했다. 이번 작업은 기능 점검과 문제 파악이며 제품 코드를 수정하거나 배포하지 않았다. 단독 검토이며 팀 검토는 실행하지 않았다.

이 프로젝트는 수동 입력한 보유 자산을 평가하고 목표·리밸런싱을 계산하며, 별도 실험실에서 과거 전략을 비교한다. 관심종목 종가 조건과 메일 작업도 구현되어 있다. 검증 규모는 기존 인수 테스트의 50명·100종목·활성 규칙 5,000개로 잡았다.

**판정: 기존 테스트가 통과해도 모든 기능이 정상인 상태는 아니다.** 저장 장애 복구 시 편집 내용 소실, 위젯 변경에 따른 자산 업로드, 환율 기준일이 다른 일간 증감, 빈 저장 버전의 무조건 덮어쓰기를 재현했다. 운영 거시경제 지표 4개는 반복 조회에서 모두 실패했다.

## 우선 수정할 문제

### 1 저장 장애 후 편집 내용이 복구 과정에서 사라짐

**영향:** 계정에 저장했다고 기대한 최근 수정이 다른 기기에 반영되지 않으며, 장애가 해소된 뒤 브라우저에서도 사라질 수 있다. 데이터 보존 문제이므로 우선순위가 가장 높다.

**재현:** 서버·브라우저 현금 100, 기존 `-before-cloud` 복구본 50을 준비한다. 계정 조회에 503을 반환한 뒤 현금을 200으로 저장하면 서버 요청은 0회이고 브라우저만 200이 된다. 다음 정상 조회에서 서버의 100을 받으면 화면과 브라우저가 100으로 바뀌고 복구본은 50으로 남는다. 어느 백업에도 200이 없다.

**원인:** [dashboard.js](../../app/static/dashboard.js)의 `loadCloudState`는 설정 미완료와 일시 조회 실패를 모두 `cloudReady=false`로 처리한다. `persistState`는 이 상태에서 브라우저 저장을 성공 처리한다. 이후 서버 조회는 로컬 값을 덮어쓰며, `-before-cloud`는 처음 한 번만 기록된다. 화면에 브라우저 저장 안내는 있지만 미동기화 초안을 복구하는 경로는 없다.

**최소 수정 방향:** 저장소 미설정과 조회 실패를 구분한다. 조회 실패 상태에서는 계정 저장 완료 흐름으로 진행하지 않고 입력을 유지하며 조회 재시도를 제공한다. 이미 존재하는 미동기화 로컬 변경도 서버 값 적용 전에 별도 보존하고, 사용자 선택 없이 서버에 덮어쓰지 않는다.

**회귀 기준:** 조회 503 → 편집 → 재시도/재접속에서 초안 보존, 기존 복구본이 있는 경우, 로컬 저장 차단, 실제 타 기기 revision 충돌을 함께 검증한다. 임시 재현: `node output/audit-save-recovery.cjs`.

### 2 운영 거시경제 지표 4개가 조회 불가

**영향:** 실효 연방금리 DFF, 10년 국채금리 DGS10, CPIAUCSL, 실업률 UNRATE 위젯을 이용할 수 없다.

**확인:** 운영 `GET /api/dashboard/markets`는 HTTP 200이지만 두 차례 조회에서 네 항목 모두 `available=false`였다. 같은 응답의 주가지수·VIX·환율은 정상이다. 로컬 `macro_observation`은 네 지표 모두 정상 반환했다. 따라서 단순 HTTP 상태 확인으로는 이 장애를 잡지 못한다.

**원인 범위:** [dashboard.py](../../app/services/dashboard.py)의 FRED HTTP·파싱 경로를 조사해야 한다. `macro_item`은 모든 예외를 동일한 조회 불가 응답으로 바꾸며 구체적인 원인을 남기지 않는다. Vercel 메타데이터 조회는 현재 자격증명으로 403을 반환해 배포 버전과 런타임 로그를 확인하지 못했다. 네트워크 차단·TLS·타임아웃 중 어느 것인지 확정하지 않았다.

**최소 수정 방향:** 배포 환경에서 실패 예외 종류와 HTTP 상태를 비밀값 없이 확보한 뒤 원인에 맞춰 수정한다. 화면은 부분 실패를 계속 명시하고, 모니터링은 200 여부뿐 아니라 항목별 `available`과 관측일을 확인한다. 데이터 공급자 교체는 원인 확인 전 결정하지 않는다.

**회귀 기준:** 정상 CSV, 누락 값, 잘못된 응답, 연결 실패의 로컬 검사와 배포 후 네 지표의 실제 조회를 별도로 통과시킨다.

### 3 환율 기준일 불일치에도 일간 증감을 표시

**영향:** 서로 다른 기간의 주가 변화와 환율 변화를 합친 값을 일간 자산 증감으로 보여준다. 휴장일 차이나 지연된 환율 응답에서 발생할 수 있다.

**재현:** AAPL 10주, 원화 현금 140,000, 달러 현금 100을 원화로 평가한다. 주가 200/190은 10월 23일/22일, 환율 1400/1300은 10월 21일/20일로 제공한다. 현재 코드는 `dayChange=340000`을 반환한다.

**원인:** [dashboard.py](../../app/services/dashboard.py)의 `same_previous_date`는 보유 주식끼리의 현재·이전 날짜만 비교한다. 환산에 사용한 환율의 두 날짜는 비교하지 않는다. 기존 날짜 불일치 테스트도 두 주식의 날짜만 다르게 만든다.

**최소 수정 방향:** 외화 자산이나 외화 현금 때문에 환산이 필요한 경우 환율의 현재·이전 기준일까지 일간 증감 계산 조건에 포함한다. 불일치하면 일간 증감·증감률을 보류하고 최신 평가액과 날짜는 계속 표시한다. 환율을 사용하지 않는 동종 통화 자산은 영향을 받지 않게 한다.

**회귀 기준:** 현재 환율 날짜만 불일치, 이전 날짜만 불일치, 외화 현금만 존재, 환산 불필요, 모두 일치하는 경우. 임시 재현과 정상 계산 대조: `.venv/Scripts/python.exe output/audit-calculations.py`.

### 4 위젯 변경이 브라우저 자산을 계정에 업로드

**영향:** 서버 저장 정보가 없는 계정에서 자산 업로드 버튼이나 자산 저장을 누르지 않고 위젯을 숨기기만 해도 기존 브라우저 자산이 서버로 전송된다. README의 기존 브라우저 정보는 자동 업로드하지 않는다는 동작과 다르다.

**재현:** 브라우저 현금 100, 서버 상태 없음, `revision=null`인 상태에서 목표 위젯을 숨긴다. 자동 저장 요청에 배치와 함께 현금 100을 포함한 전체 자산이 들어간다.

**원인:** [dashboard.js](../../app/static/dashboard.js)의 `savePanelLayout`이 전체 `state`를 `persistState`에 전달한다.

**최소 수정 방향:** 명시적인 최초 자산 업로드 전에는 위젯 배치만 로컬에 보존한다. 기존 서버 자산이 있거나 사용자가 자산 업로드를 완료한 뒤 계정 배치 자동 저장을 허용한다. 새 부분 저장 API는 필요하지 않다.

**회귀 기준:** 기존 로컬 자산 + 빈 서버에서 위젯 숨김/이동/크기 변경이 자산을 전송하지 않는지 확인하고, 명시적 업로드 후 배치 저장·복원을 검증한다. 첫 번째 문제와 같은 임시 재현 스크립트에 포함했다.

### 5 빈 revision이 충돌 검사를 우회

**영향:** 일반 화면이 보내는 정상 값에서는 발생하지 않지만, API가 `revision=""`인 요청을 받으면 동시 수정 보호 없이 같은 계정의 자산을 덮어쓸 수 있다.

**재현:** `SaveDashboardRequest`는 빈 문자열을 허용한다. `save_state`는 `revision is None`이 아니므로 `create=False`를 전달한다. 실제 `PortfolioStore.write`는 빈 문자열을 거짓으로 판단하여 `x-if-match` 없이 `x-allow-overwrite=1`을 전송한다. 모의 HTTP 전송으로 이를 확인했다.

**최소 수정 방향:** 저장 요청 스키마의 revision에 최소 길이 1을 적용해 빈 문자열을 422로 거부한다. `None`의 신규 생성 의미와 내부 알림 상태 파일의 의도적인 무조건 쓰기는 유지한다.

**회귀 기준:** 빈 문자열 422, `None` 최초 생성, 정상 revision 수정, 오래된 revision 충돌. 실제 HTTP 어댑터까지 확인한다. 기존 메모리 저장소는 빈 문자열도 불일치로 거절하므로 이 차이를 숨긴다.

## 테스트 보강 우선순위

1. 저장 복구·최초 업로드·빈 revision의 재현을 지속 회귀 테스트로 옮긴다. 화면 테스트는 실제 `loadCloudState`와 `persistState`를 함께 실행해야 한다.
2. 환율 기준일을 포함한 일간 증감 검사를 추가한다.
3. 기본 테스트 결과에서 단위·DB·브라우저·실서비스 검증 여부를 따로 표시한다. `scripts/test.ps1`과 WSL 스크립트는 현재 pytest만 실행하며, DB 설정이 없으면 중요 검사가 건너뛰어진다.
4. 배포 후 읽기 전용 점검은 응답 코드뿐 아니라 기능 결과를 검증한다. 거시지표는 HTTP 200에도 전체 항목이 실패할 수 있다.

화면 VM의 `tests/helpers/dashboard.cjs`는 기본적으로 `loadCloudState`, 시세 조회 함수를 빈 함수로 교체한다. Chrome 검사도 fetch를 교체한다. 따라서 이 테스트들만으로 클라우드 읽기·쓰기·복구나 공급자 계약의 정상 동작을 보장할 수 없다. 새 테스트 프레임워크나 일반적인 추상화 추가보다 위 경계의 실제 처리 코드를 실행하는 작은 회귀 검사가 우선이다.

## 최종 검증 기록

`ALERT_TEST_DATABASE_URL`을 새 로컬 DB에 지정하고 `ALERT_RUN_LOAD_TEST=1`로 전체 pytest를 실행했다. **263개 통과, 실패 0, 건너뜀 0, 총 392.93초**였다. 앞서 실행한 Node 25개와 Chrome 3종도 통과했다.

부하 검사는 사용자 50명·종목 100개·규칙 5,000개를 대상으로 했다. 종목 조회는 중복 없이 100회, 신호 5,000건, 메일 공급자 접수 상태의 원장 50건을 확인했다. 처리 호출 3회의 소요 시간은 **166.28초, 151.60초, 54.77초**로 각 호출의 검사 기준 210초 미만이었다. 시세·발송 HTTP와 대기 시간은 모의 구현이며 이 수치로 운영 공급자의 처리량을 보장하지 않는다. 측정 결과는 `output/stock-alert-load.json`에 있다.

추가 재현 스크립트 두 개는 `output/`에 보관했다. 정상 기능 검사는 독립 수식과 비교했고, 결함 검사는 현재의 잘못된 동작이 발생하는지 assert로 확인했다. 이 스크립트의 성공은 결함이 수정됐다는 뜻이 아니다. `output/`은 Git 제외 대상이므로 공유 시 보고서의 재현 조건도 함께 사용한다.

운영 계정 데이터 변경, 실제 이메일 발송, 배포, 커밋·푸시는 수행하지 않았다. Vercel 관리 API 403으로 운영 설정·배포 버전·로그는 미확인이다. 알림의 실제 공급자·메일 설정은 로컬에 없으며, 기본 `vercel.json`에는 신규 종가 알림 Cron이 없다. 활성화 절차는 [알림 운영 문서](../stock-alerts-operations.md)에 분리되어 있으므로 로컬 DB 테스트 통과를 운영 발송 활성화로 해석하면 안 된다.
