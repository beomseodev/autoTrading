# 추가 서버 없는 국내 해외주식 자동매매 검토

작성일: 2026년 10월 23일. 코드 기준: `a54986f`.

상태: **조사와 팀 검토 완료. 방향 결정 및 구현 착수 전.**

기존 Vercel 프로젝트에서 한국투자증권 개인 API를 직접 호출하면 별도 매매 서버와 고정 IP 없이 자동 리밸런싱을 구현할 수 있는 근거가 확보됐다. 다만 실제 배포 접속과 계좌별 주문 권한은 검증 전이다. 아래 실행 방식과 증권사 선택은 비교 후보이며 확정된 구현 계획이 아니다.

## 사용자 목표와 제약

- 본인 계좌의 국내주식과 해외주식을 자동으로 매매한다. SCHD, TQQQ, QQQI 같은 미국 상장 ETF를 직접 다루는 것이 범위에 포함된다.
- 페이지에 설정한 목표 비중과 허용 오차에 따라 리밸런싱 신호가 발생하면 실제 매도와 매수를 수행한다.
- 체결 결과와 최종 잔고를 확인하고 페이지 갱신 및 결과 알림까지 연결한다.
- 추가 VM, 매매 서버, 고정 IP, 상시 켜진 개인 PC를 전제로 하지 않는다.
- 추가 서버가 없다는 조건과 추가 비용 또는 관리형 서비스가 전혀 없다는 조건은 다르다. Vercel 요금제 변경, 관리형 DB, Workflow 도입 여부는 향후 결정한다.
- 자동주문은 우선 본인 계좌 범위다. 일반 사용자 대상 종가 알림 확장과 타인 계좌 주문 대행은 별개다.

기존 [종가 알림 확장 계획](../plans/2026-10-23-stock-alerts.md)은 알림 기능의 계획이다. 그 문서의 인프라 제안이나 일반 사용자 지원 범위를 자동매매에 그대로 적용하지 않는다.

## 현재 프로젝트 상태

| 항목 | 현재 상태 |
| --- | --- |
| 실행 환경 | Python 및 FastAPI, Vercel 배포 |
| 예약 실행 | `vercel.json`의 `/api/cron/rebalance`, 매일 01:00 UTC인 한국시간 10:00 |
| 함수 제한 설정 | `app/main.py`의 `maxDuration` 300초 |
| 현재 Cron 동작 | 리밸런싱 평가와 이메일 알림. 실제 주문 기능 없음 |
| 보유 정보 | 사용자가 입력한 수량 기반. 자동주문 전 실제 증권사 잔고와 대조 필요 |
| 저장소 | 비공개 Vercel Blob. 단일 객체 ETag 조건부 쓰기와 생성 충돌 처리 존재 |
| 증권사 연동 | Toss 조회용 코드가 있으나 KIS 국내·해외 주문 어댑터는 없음 |
| 운영 계정 | 실제 Vercel 요금제와 실행 리전은 미확인 |

300초라는 현재 설정 때문에 별도 상시 서버가 반드시 필요한 것은 아니다. 짧은 실행에서 주문을 제출하고 상태를 저장한 뒤, 다음 실행에서 체결을 확인하는 방식이 가능하다. 다만 현재 일일 알림 Cron과 중복 발송 방지 코드는 주문 장부를 대신하지 못한다.

## 확인된 공식 근거

### 한국투자증권의 IP 정책

한국투자 공식 FAQ는 별도 IP 화이트리스트 없이 전체 허용한다고 설명한다. 다른 FAQ도 특정 IP 허용 목록이나 특정 IP 차단을 운영하지 않는다고 안내한다. 팀 검토 후 주 세션에서도 공개 JSON 원문 두 건을 직접 조회해 재확인했다.

- [화이트리스트 IP 등록 정책 공식 원문](https://apiportal.koreainvestment.com/api/forums/10000000-0000-0011-0000-000000000002/posts/691e2917-3eb9-486b-b94c-9630a5c186c6)
- [특정 IP 허용 요청 공식 원문](https://apiportal.koreainvestment.com/api/forums/10000000-0000-0011-0000-000000000002/posts/ff32a7fd-f6fc-4cb9-bfac-cb094eff4b62)

따라서 동적 출구 IP 자체를 개인 API 사용의 필수 차단요인으로 볼 근거는 없다. 제휴 프로세스의 IP 등록 조건을 개인 API에 일반화하지 않는다. 이 정책이 실제 Vercel 배포의 연결·인증 성공이나 모든 계좌의 거래 권한까지 보장하는 것은 아니다.

### 해외주식 주문과 인증

한국투자 공식 저장소는 미국 거래소 주문, 예약주문, 체결내역 조회 예제를 제공한다. 미국 주문 예제에는 실전·모의 구분과 주문유형별 제한이 있다. 모의투자 지정가 주문 성공을 다른 실전 주문유형까지 검증한 것으로 취급하지 않는다.

- [미국 주식 주문 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/overseas_stock/order/order.py)
- [해외주식 예약주문 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/overseas_stock/order_resv/order_resv.py)
- [해외주식 체결내역 조회 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/overseas_stock/inquire_ccnl/inquire_ccnl.py)
- [인증 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_user/kis_auth.py)

인증은 App Key와 Secret 기반이다. 여러 함수가 동시에 토큰을 발급하지 않도록 공유·갱신 제어가 필요하다. SCHD·TQQQ·QQQI의 개별 거래 가능 여부, 계좌 해외거래 신청, 필요한 상품 거래 자격은 별도 확인한다.

### Vercel 실행 조건

Hobby Cron은 각 작업이 하루 한 번이며 지정 시간대 안에서 지연될 수 있다. Pro는 분 단위 실행을 지원한다. Cron은 실패 자동 재시도가 없고 누락·중복·동시 실행을 고려해야 한다. 현재 01:00 UTC 실행을 미국 정규장 주문 시각으로 간주하면 안 된다.

- [Cron 요금제와 한도](https://vercel.com/docs/cron-jobs/usage-and-pricing)
- [Cron 실패와 동시 실행 관리](https://vercel.com/docs/cron-jobs/manage-cron-jobs)

Vercel Workflows는 관리형 상태 보존과 대기·재개를 제공한다. 공식 Python 가이드는 FastAPI 형태의 시작 예제와 자원 소비 없는 durable sleep을 안내한다. Python SDK는 베타다. 프로젝트의 Python 버전은 최소 조건을 충족하지만 SDK와 entrypoint는 아직 도입하지 않았다.

- [Vercel Workflows](https://vercel.com/docs/workflows)
- [Python Workflow 시작 가이드](https://workflow-sdk.dev/docs/getting-started/python)
- [Workflow 요금과 제한](https://vercel.com/docs/workflows/pricing)

## 실행 방식 비교

| 후보 | 동작 | 장점 | 제약과 선택 조건 |
| --- | --- | --- | --- |
| Vercel Pro Cron과 주문 장부 | 1~5분마다 미완료 작업을 조회하고 주문·체결 확인을 짧게 수행 | 기존 FastAPI 구조 유지, 실행 흐름이 명확 | 요금제 확인 필요. 동시 실행 제어와 상태 복구를 직접 구현 |
| Vercel Python Workflows | Cron 또는 서버 요청으로 시작하고 대기·조회·재개를 관리형 실행에 위임 | 별도 서버 없이 체결 대기와 재배포 후 재개 가능 | Python 베타, 도입·배포 검증 필요. 자동 재시도가 중복 주문을 해결하지 않음 |
| 현재 일일 Cron과 예약주문 | 미국 장 전 예약하고 다음 실행에서 체결과 잔여 비중 확인 | 기존 실행 주기를 유지하는 작은 변경 | 매도 후 매수와 비중 복원이 여러 거래일 걸릴 수 있음. 당일 실패 복구에 제한 |

팀장 제안은 Pro Cron을 우선 운영 후보로, Workflows를 대안으로 검증하는 것이다. 그러나 사용자는 문서화 후 방향을 정하기로 했으므로 어느 방식도 채택 확정하지 않는다. 추가 클라우드 서비스를 최소화하는 것이 우선이면 Workflows 검증의 우선순위가 높아질 수 있다.

주문 상태 저장에는 관리형 PostgreSQL 같은 관계형 DB를 검토할 수 있다. 자체 서버 운영은 없지만 추가 서비스다. 기존 Blob은 단일 객체 조건부 쓰기를 제공하며, 계좌·주문·예약 현금을 함께 갱신하는 트랜잭션을 보장하는 저장소로 가정하지 않는다. DB 도입과 Blob 활용 범위도 미확정이다.

## 모든 후보에 필요한 주문 처리

기본 흐름은 실제 잔고 조회 → 신호 판단 → 주문 계획 저장 → 초과 비중 매도 → 체결·주문가능금액 확인 → 부족 비중 매수 → 잔고 대조 → 페이지와 알림 갱신이다.

- **중복 방지:** 같은 계좌에 여러 실행이 동시에 주문하지 않도록 선점과 주문 의도 식별자를 저장한다.
- **불확실한 접수:** 주문 접수 뒤 응답이 유실되면 실패로 단정하지 않고 `unknown`으로 저장한다. 주문내역 대조 전 자동 재전송을 금지한다.
- **체결 기준:** 매도 접수만으로 매수 가능 현금을 늘리지 않는다. 실제 체결과 증권사 주문가능금액을 확인한다.
- **부분 체결과 취소:** 누적 체결량을 대조하고 취소 요청과 취소 완료를 구분한다. 미완료 주문이 있는 상태에서 새 리밸런싱을 중복 시작하지 않는다.
- **시장과 통화:** 미국 서머타임·휴장·조기폐장, 한국과 미국의 다른 거래일, KRW와 USD 예수금·환율을 구분한다.
- **수량 계산:** 정수주 반올림, 최소 주문단위, 수수료 여유, 허용 오차를 반영한다. 그룹 목표를 종목별 주문으로 바꾸는 내부 배분 규칙이 필요하다.
- **비밀정보:** 계좌 키와 토큰을 브라우저·대화·Workflow 입출력 로그에 노출하지 않는다.

Workflow의 자동 재시도나 DB 트랜잭션만으로 증권사 외부 주문의 정확히 한 번 실행을 보장할 수 없다. 증권사 접수 결과와 내부 장부를 대조하는 절차가 공통 필수다.

## 향후 결정 항목과 검증 순서

방향 결정 때 아래 항목을 선택한다. 현재 문서는 기본값을 확정하지 않는다.

1. 한국투자 계좌를 사용할지, 다른 증권사를 더 비교할지.
2. 당일 매도 후 매수 완료가 필요한지, 여러 거래일에 걸친 비중 복원이 허용되는지.
3. Vercel Pro 사용과 관리형 DB 추가를 허용할지.
4. Python 베타 Workflow를 검증 대상으로 받아들일지.
5. 환전을 자동화할지, 준비된 달러 예수금 안에서만 거래할지.
6. 그룹 안 종목별 배분, 주문유형, 가격 한도, 미체결 중단·취소 기준을 어떻게 정할지.

방향 결정 후 검증은 다음 순서로 진행한다.

1. 실제 Vercel 플랜과 리전을 확인한다.
2. 배포 환경에서 한국투자 인증·잔고·종목 조회를 비주문 방식으로 확인한다.
3. 모의 미국 주문·취소·체결 조회를 확인하고 대상 ETF별 계좌 자격을 점검한다.
4. 가짜 API로 중복 호출, 응답 유실, 저장 실패, 부분 체결, 재배포 중단을 재현한다.
5. 선택한 실행 방식에서 복구와 중복 주문 방지를 확인한 뒤 별도 실거래 범위를 정한다.

현재 단계에서 인증 호출, 모의·실제 주문, 운영 배포 변경은 수행하지 않았다. Vercel과 KIS의 동일 구성으로 실제 자동 리밸런싱까지 성공한 공개 사례도 이번 조사에서 확보하지 못했다. 공식 지원 근거와 운영 검증 결과는 구분한다.

## 팀 검토 참여와 판단 차이

실제 Orca 작업자 네 명이 독립 검토했고 모두 완료 보고 후 해제했다. 누락이나 공급자 대체는 없다. 각 작업자는 지정 보고서만 작성했으며 제품 코드는 변경하지 않았다.

| 역할 | 핵심 결과 |
| --- | --- |
| 비판 | 공식 IP 전체 허용 정책 확인. 인증·계좌 권한과 주문 불확실성은 별도 검증 필요 |
| 가능성 | 일일 예약주문, Pro Cron, Python Workflows의 세 경로와 LS 후보 확인 |
